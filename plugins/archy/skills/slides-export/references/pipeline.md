# Slides export pipeline: technical reference

Read this when running, debugging or changing the Paper → `.pptx` export. `SKILL.md` has the procedure; this file has the reasons, the conversions, the item types and every footgun found so far.

Tools live in `${CLAUDE_PLUGIN_ROOT}/tools/slides-export/`. Working data and output live in `${CLAUDE_PLUGIN_DATA}/slides-export/<project>/`.

---

## Why a generator, and why it is cheap

Paper exports only `png / jpg / webp / avif / pdf / svg`, so there is no editable-text path out of it. A `.pptx` has to be **generated** from Paper's own values.

That is cheap rather than a rewrite because `get_children` returns `worldX` / `worldY` for every node: **Paper has already resolved the flex layout**. The generator flattens the tree to absolutely positioned leaves and emits them one for one. It never reimplements flexbox.

The round trip is proven in the other direction too: the Archy source deck **came out of** Google Slides (`ppt/fonts/Onest-regular.fntdata` and per-weight family names like `Onest SemiBold` are its exporter's signature), so Onest and Inter exist in the Slides font picker.

Paper's own `export` writes to `~/Downloads`, which macOS TCC blocks scripts from reading. That is another reason to generate from source rather than export by hand.

## Two cases: the template library and a real deck

| | Template library | A real deck |
|---|---|---|
| Specs | `specs.js`, written by hand | Generated by `paper2spec.js` from MCP reads |
| Why | The 55 layouts *are* the design system; writing them out is how they were verified | Dozens of one-off artboards that already exist; hand-writing a spec is transcription, and every line is a chance to mistype a coordinate |
| Meta page number | `NN` placeholder, filled by `build.js` from slide position | Whatever the deck carries |
| Headline leading | `"single"` | Paper's exact `line-height` |
| Partial build | Unsafe (numbers from 1) | Safe if the meta carries no page number |

## Slide size and the conversions

**The exported slide is 18 × 10 in**, a `sldSz` of 16459200 × 9144000 EMU. That is not one of pptxgenjs's presets, so `build.js` calls `defineLayout` before the first `addSlide`; `LAYOUT_16x9` would silently produce a 10 × 5.625 deck instead.

| Canvas px → | |
|---|---|
| Position and size | **× 8572.5 EMU**, or `px × 3/320` inches |
| Font size and line height | **× 0.675 pt**: 128 → 86.4pt, 60 → 40.5pt, 22 → 14.85pt |
| Tracking (`em`) | `em × px × 0.675` pt, emitted as `charSpacing` |

**The map is by width, and that is a decision, not arithmetic.** The canvas is 16:9 (1.7778) and an 18 × 10 slide is 1.8, so one axis has to give. Scaling 1920 px to 18 in puts the content column's margins at a symmetric 0.9 in and sends y=1080 to 10.125 in, 0.125 in past the bottom edge. Nothing is lost there, because the foot-cap Ruler sits at y=1056 (9.9 in) and everything below it is margin. Mapping by height instead fits 1080 px into 10 in exactly but leaves 0.22 in of dead width on the right, so the design stops filling the frame. **Check the foot cap before changing the target size again**: it is the lowest ink on the canvas, and it is what makes a width-first map safe.

**Superseded constants.** The earlier values (× 4762.5 EMU or `px / 192` in, × 0.375 pt, so 128 → 48pt, 60 → 22.5pt, 22 → 8.25pt) came from a 10 × 5.625 in `sldSz` (9144000 × 5143500 EMU). They no longer apply. `build.js` is shared, so the 55-layout template library exports at 18 × 10 too.

## Fonts

Use the per-weight family names (`Onest`, `Onest SemiBold`, `Inter`, `Inter Medium`, `Inter SemiBold`) and **never a bold flag**. Those are the exact names Google Slides uses.

**`write_html` normalises a per-weight family back to the bare one**, storing `"Inter", system-ui, sans-serif` with `fontWeight: 500`. `paper2spec`'s `fontFace()` therefore recovers the face from `fontWeight` when the family carries no hyphen (500 → Medium, 600 → SemiBold, 700 → Bold). Without that, a 96px SemiBold title exported as regular Inter.

## Spec format (`build.js` input)

Everything is in **canvas px** and hex **without `#`**. A `#` or an 8-digit hex with alpha corrupts the file; use `transparency: 0-100`.

```jsonc
{ "type": "rect",    "x": 0, "y": 20, "w": 1920, "h": 2, "fill": "EEEEEE" }
{ "type": "ellipse", "x": 136, "y": 936, "w": 72, "h": 72, "fill": "CCEAFF" }  // portraits, dots
{ "type": "pill",    "x": 136, "y": 440, "w": 81, "h": 34, "fill": "E6F4FF" }  // Status pill
{ "type": "image",   "x": 1464, "y": 856, "w": 360, "h": 140, "src": "assets/archy-wordmark.png" }

{ "type": "text", "x": 148, "y": 544, "w": 700, "h": 96,
  "text": "…", "font": "Inter", "size": 22, "line": 32, "color": "666666" }
```

- `"upper": true` uppercases the string, because OOXML has no `text-transform` and Paper stores the untransformed text.
- `"line"` takes a number in canvas px (emitted as exact point spacing, mirroring Paper's `line-height`) or the string `"single"` (100%, the font's own metrics).
- `line` is a segment: pptxgenjs draws from `(x,y)` to `(x+w,y+h)`, so an upward slope is `flipV: true`.
- `polygon` is the area wash under a line chart, via `custGeom` (pptxgenjs has no polygon primitive). `validate.py` confirms PowerPoint accepts the geometry.
- `build.js` accepts a single `.json` spec, a `.js` module, or a generated specs file. It also accepts `--only=`.

### The two-tone headline

Use `runs` instead of `text`: **one text box, several coloured runs**, not one box per line.

```jsonc
{ "type": "text", "layer": "Headline", "x": 96, "y": 144, "w": 1728, "h": 140,
  "runs": [
    { "text": "Dental practices run on decades-old server-based software", "color": "00004E" },
    { "text": "and drown in administrative work.", "color": "666666" }
  ],
  "font": "Onest SemiBold", "size": 60, "line": "single", "track": -0.02 }
```

**This applies to every layout, not per slide.** Wherever a `Headline` frame holds stacked text nodes at `gap: 0`, they collapse into one item with one run each. The two Paper nodes are a workaround for Paper not being able to colour part of a text node; OOXML runs are native, so the export expresses the device as designed (a colour split mid-sentence) and the team gets one editable field instead of two. **Paper keeps showing two nodes forever; that is correct, the merge lives only in the exporter.**

Keep an explicit line break between the runs. Without it the colour boundary is anchored to a character position, so re-written copy can slide it into the middle of a line.

### Leading

- **Template library:** headlines take Single (`spcPct` 100%). Reviewed in Slides, a headline reads better letting the font's metrics govern than pinned to 70px as exact points, and it survives someone changing the size. Do **not** extend Single to wrapping body copy: 22/32 is a deliberately open measure and Single tightens it to about 1.2×.
- **A real deck:** leading stays exact for everything, headlines included. A deck is reviewed slide by slide against the canvas, so leading that drifts from Paper reads as a bug. The extractor emits Paper's `line-height` throughout.

### Template-library helpers (`specs.js`)

All fifty-five layouts live in `specs.js` as a module, so the parts that are identical by construction (the Rulers frame, the Meta line, the three-part header) are written and verified once. Shared pieces: `meta()`, `eyebrow()`, `headline()`, `lightFrame()`, `footerFrame()`, `captureSlot()`, `logoSlot()`, `polyline()`. Each layout supplies only its own body data. Slides come out **grouped by the seven library categories** (`CATEGORY_ORDER` in `build.js`).

- **Image slots** are `rect` items filled `EEEEEE` with a centred `CAPTURE` label; `captureSlot()` builds the pair. A full-bleed slot fills `666666` so white type and Rulers read on it, and it must be the **first** item in the array or it covers the Rulers, Meta and eyebrow.
- **The meta page number is `NN`** on every template; `build.js` substitutes the real number from the slide index.

## Charts

**Drawn from `rect` items. Never `addChart`.** The generic pptx advice is to keep charts native, which is right for PowerPoint and **wrong for Google Slides: a native pptx chart imports as a flat image.** That loses the editable data the native route existed for, and loses what rectangles keep: real shapes a person can still select, recolour and resize. Tested by building the same slide twice into one file (drawn vs `addChart`, identical outside the plot) and importing it. `build.js` has **no chart item type**, on purpose. Do not re-litigate without re-running that test.

- **Every chart shares the baseline `CHART_BASE = 976`.** Each scales its own peak to leave room for its labels: 490 for the full-width plots, 400 for `Chart + Hero Number`'s narrower column, **440** for `Waterfall` (its tallest point is the middle step with a label above it; at 490 that label lands at y −20).
- **Bar heights are derived from the data, never authored.** `BARS` in `specs.js` holds `[value, label, year, isForecast]`; `barHeight()` scales each value against the tallest so the peak lands on `BAR_MAX` (490px). Heights are rounded to integers. Real numbers are a one-line change: replace the values and labels, and the geometry follows.
- **Stacked segments come from cumulative boundaries**, not from scaling each segment. Rounding each segment independently lets the parts drift off the total.
- **`Cohort Curves`** emits its three polylines as `line` segments via `polyline()` (18 segments across three series). They stay selectable shapes in Slides.
- **On a dark ground the series colours invert.** `--color-royal-blue-500` disappears against navy, so dark charts step `--color-sky-blue-400` → `--color-blue-tint-300` → `--color-blue-tint-200`.

## Generating specs for a real deck (`paper2spec.js`)

Two MCP reads per artboard:

| Read | Gives |
|---|---|
| `get_tree_summary` (depth 10) | id, component, name, **resolved w × h**, text |
| `get_computed_styles` (batched) | font, size, leading, colour, fill, flex, padding |
| `get_children` (optional) | `worldX` / `worldY`, for spot-checks and pins only |

**It resolves flex itself, and that is safe for one reason: every size is Paper's.** The hard half of flexbox is measuring wrapped text, and Paper has already done it, so the script only *places* boxes it never measures. It covers flex row/column with gap, `padding` in every shorthand Paper emits (`paddingInline` / `paddingBlock` turn up as often as the long-hand pair), `justify-content` including `space-between`, `align-items`, `align-self`, `margin-*: auto`, percentage `left` / `top`, and `translate`.

**Pin measured coordinates in the dump's `coords` map as a regression test.** Pins override, and a disagreement is *reported before it is applied*: silently correcting one would hide the case the resolver cannot model, which is why pins exist. Example: a Cover ships with all fifteen of its real positions pinned.

### Headline merge, done structurally by the extractor

It covers two shapes of the same device:

- **A column at `gap: 0`**: the headline that wraps. Runs join with a line break.
- **A row on the baseline or centred**: the headline that fits on one line, where the gap stands in for the word space. Runs join with a real space, and a run may carry its own `fontFace`, which is what lets "**Bold lead.** Grey continuation" come out as one field.

Everything else must differ in nothing but colour or weight at the same size, so a stack with gap 6, two faces and two sizes correctly stays two items. Two guards:

- **A leading numeral blocks the merge.** `1` + `What we do` passes every structural test and is *not* this device: it is an ordinal beside a label, and merging it also swaps a 14px gap for a narrower word space and pulls the label left. The tell is position, not digits: an ordinal leads. `A day in the practice,` / `2031.` is a headline and must merge.
- **Identical colour and identical face means no merge.** Those are two deliberate paragraphs.

A column of names at `gap: 0` with some entries royal and the rest light-text at one size and face is structurally the two-tone device, and merging it is correct (one editable field, colours as runs). A column whose two names share a colour correctly stays two nodes.

**Verify in the OOXML that `lnSpc` landed on both `<a:p>` elements**, not just the first.

### What the resolver has to model

All of these were found by a pin disagreeing:

| | Why it bit |
|---|---|
| `margin-*` on a flex child | An icon's `margin-bottom: 8px` walked everything under it up by 8 |
| `padding` on a **static** child (not an absolute one) | Absolute resolves against the padding box, static against the content box (a 12px white photo mat) |
| `top: 50%` + `translate: 0 -50%` | A vertically centred Content frame; `parseFloat` reads "50%" as 50 |
| `border-radius: calc(infinity * 1px)` | NaN, and a circular portrait ships square |
| An 8-digit hex (`#FFFFFF2E`) | `hex()` drops the alpha, and a translucent disc ships solid |
| `background-position` with `cover` | One screenshot shown in two boxes at two crops |
| `overflow: clip` on an ancestor | An oversized image at a negative offset (the reframing device) |

**An absolutely positioned child of a FLEX frame is out of flow.** CSS resolves it against the padding box exactly as in a block frame, and flexbox never sees it. The resolver once checked `position` only in its non-flex branch, so six pinned bar frames came out stacked in a vertical pile at one x, each internally correct, and nothing threw. The tell: several siblings reporting the *same* x (or y) with a spacing equal to their own height plus the parent's gap.

**Rotation is modelled, and it is the one transform that does not survive as-is.** `paper2spec.js` carries a `{cx, cy, deg}` pivot down the subtree of any rotated frame and swings each leaf's own **centre** around it; `build.js` passes `rotate` to `addShape` / `addImage` / `addText`. pptx spins a shape about its own centre while Paper spins about the frame's top-left (Paper normalises `transform-origin` to `0% 0%`), so the resolver converts between the two. Sign and unit (degrees, clockwise) carry across unchanged. **Nested rotation throws** rather than composing silently.

**Borders are emitted per side, as thin rects, and deferred to the end.** pptx cannot give a shape a different border per side (a nav strip framed on three sides so its seam with the hero stays open). They are flushed last because a frame is met *before* its children, so emitted in place every hairline lands under the screenshot it outlines.

## The dump harness

`mkdump.py` plus a per-slide set of files, each saved **verbatim** from the MCP:

```
trees/NN.txt      get_tree_summary(depth 10): the `summary` string, as-is
styles/NN.json    get_computed_styles([ids]): the `styles` object, as-is
text/NN.json      optional {id: full string} for anything truncated at 60 chars
assets/NN.json    optional asset map
```

```bash
python3 mkdump.py 66 direct-mail "66 · Direct Mail"     # example: slide 66
```

`mkdump.py` only staples them together into `dump/NN-<slug>.json`, and **refuses if a node in the tree has no styles**. A path inside an SVG is exempt: `paper2spec` skips it and the whole icon goes in as one PNG, so reading its styles is dead weight. The selection for a partial build is by the dump's numeric prefix, which is also the deck order.

`get_tree_summary` truncates text at 60 characters with no marker. Put the full string from `get_node_info` into `text/NN.json` for any node that could be longer.

A shared factory module for the header, Meta and Rulers every slide shares keeps a fifty-node slide to two dozen lines instead of two hundred.

## Assets

Google Slides cannot take SVG, so vector art (the wordmark, icons, la mascota, logos) goes in as PNG.

- **`jsx2png.py <in.jsx> <out.png> [scale]`** (default scale 4.0) converts the React attribute spellings `get_jsx` returns (`fillRule`, `strokeWidth`, `stopColor`, …) back to SVG ones and substitutes tokens from `tokens.json` (a `var()` fill renders as black outside Paper). Anything left camelCase is *silently ignored* by the renderer, which is how a gradient or a fill-rule goes missing without an error. **Never retype path data: copy the markup, and check the ink is non-zero.**
- **A connector arrow is width-specific**, the one asset that cannot be reused by name. Its viewBox is the node's own width (`0 0 200 16`, `0 0 90 16`), not a 24 grid, so scaling the 200px file into an 80px box stretches the head into a wedge. One PNG per width: `arrow-right`, `arrow-right-140`, `arrow-right-90`, `arrow-right-80`.
- **Never point a new slide at an existing asset PNG on the strength of its name.** Example: a `user-group.png` already on disk was *green*, built for another slide. Read the ink with `get_jsx` on the node and generate a suffixed variant (`user-group-royal`, `-white`) rather than assuming the file matches. The same read caught an icon being **white** on its royal panel where a blue tint was the obvious guess.
- **The wordmark** is the 5-path mark off the Paper canvas, `viewBox "0 5 252 98"` in a `translate(0 21.752)` group; its 252 × 98 ink matches a 360 × 140 placement exactly. Never take it from the Webflow `index.html`: that inline SVG is missing the counter of the "A" and renders as "∩rchy".
- **Hugeicons** for the template library come straight from the `@hugeicons/core-free-icons` npm package (see the `hugeicons` skill), and the generator refuses to write an icon whose path data came back empty. An icon may exist twice, neutral and royal (`icon-verify` / `icon-verify-royal`), when layouts need both states.
- **`bk-fade-dark.png`** is the template library's one scrim (`Capture + Scrim`): 1920 × 680, transparent to `#00004E` by 65% of its height, generated with Pillow.

### Gradients

**pptxgenjs supports no gradient fills at all.** A gradient ground goes in as a background image and stops being an editable shape. That is why the thirteen dark template layouts sit on flat `--color-dark-background`.

**`make-gradients.py` renders every CSS gradient the dumps reference to a PNG, in Oklab**, because that is what the canvas says (`linear-gradient(in oklab …)`). The same two blues lerped in sRGB desaturate through the middle and read as a different ground.

### Photos

**Photos live on Paper's CDN, not on disk.** `get_computed_styles` reports `url(https://app.paper.design/file-assets/…)`. **`fetch-photos.py`** caches every referenced image by asset id, so the deck rebuilds offline and a re-run costs nothing. The CDN **403s a bare urllib request**; the script sends a browser User-Agent.

**`shrink-media.py` is a required last step on a photo-heavy deck.** The CDN hands back the *original upload*, so a 2000px portrait ships inside a 208px well and the file leaves `build.js` at 68 MB. Capping every raster at 3× its largest placement takes it to 23 MB with nothing visible lost, and Google Slides has to convert every one of those pixels on import. Vector-derived assets are already generated at 4× their box and are left alone by the same rule.

## Build and timings

`export.sh` takes a slide range; a partial build is the normal case:

```
export.sh              every dump
export.sh 94           one slide     (~0.8s)
export.sh 66-70        a range       (~1.7s)
export.sh 66-70,94 out.pptx
```

The whole deck takes ~8s. The cost is almost entirely `build.js` embedding media plus `shrink-media.py` resampling it, so it scales with the number of slides requested. Internally: `paper2spec.js` → `build.js` → `postprocess.py` → `shrink-media.py`.

**A partial build is safe only when the deck's meta carries no page number.** In the template library the meta is `NN` and `build.js` fills it from position, so a partial build there would number from 1.

**Do not rebuild and re-send the deck unless it was asked for.** Editing a slide is not a request to export it.

## pptxgenjs footguns

- **`letterSpacing` is silently ignored.** The option is `charSpacing`, in points.
- **Autofit.** `fit: "none"` emits *no* autofit element, which in OOXML means "inherit". Google Slides is then free to shrink text on overflow, and the type scale is silently lost the moment someone types a longer headline. `postprocess.py` injects an explicit `<a:noAutofit/>` into every text body and rewrites the `.pptx` in place. **It is not optional.** Overflowing is the correct failure: visible, and gets fixed. Shrinking is invisible and breaks the scale.
- **`margin: 0` on every text box.** The built-in inset otherwise pushes text off the Ruler it should align with.
- **`breakLine: true` produces two `<a:p>` paragraphs**, not an `<a:br/>`. Fine, but check `lnSpc` landed on both; on only the first, the second line drifts.
- **Hex colours: no `#`, no alpha.** Both corrupt the file. Use `transparency: 0-100`.
- **Gradient fills are not supported.** See *Gradients*.
- **No 16:9 preset at 18 × 10.** Call `defineLayout` before the first `addSlide`.

## Renderer health

**A stuck renderer poisons this pipeline silently.** Check before a long run. The tell: a text node reporting `0×0` and its parent frame `1728×0` while fixed-height frames still report correctly. See `brand/references/paper-quirks.md` (*Renderer and reading geometry*) for the diagnostic, and do not derive a coordinate while it is down. A *single* unresolved read right after the file regains focus is harmless: re-read and it settles.

`get_children` on an inactive page returns unresolved layout (`x` / `y` as 0). `open_file` with the artboard's `pageId` before reading any geometry.

## Checking the output

```bash
python3 <pptx-skill>/scripts/office/validate.py out.pptx   # must print PASSED
markitdown out.pptx                                        # every string present?
```

There is no local visual render, and it would only be a proxy anyway. **Google Slides is the real renderer; check it there.** Look at:

- tracking on the uppercase labels
- Ruler weight (2 canvas px)
- where the body lines break
- then type a longer headline and confirm nothing shrinks

Re-check after any change to tight quote-mark line boxes (80/28, 120/40), very large type (180pt), or any layout that sets type in a line box smaller than its font size. That is the pattern CSS and PowerPoint disagree about.

Verify copy by extracting every `<a:t>` run and diffing it against the Paper text (read with `get_node_info`, not `get_tree_summary`).
